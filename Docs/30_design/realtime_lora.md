## 0. この文書が決めること

**サーバーが持つ天気・混雑の値を、観光中の端末にどうやって届けるか**を確定させる(FR-4.4 / FR-4.5 / NFR-9)。

**この文書の位置づけ**: ユーザー指示(2026-08-01)により、**LoRaWAN 周りは作り込まない**。要求を満たす最小の形を決めて実装に渡す。凝った符号化・適応的スケジューリング・ACK 再送などは**やらない**。

**この文書で決めないもの**: 端末側の再生ロジック([offline_field_mode.md](offline_field_mode.md))、variant の語彙([ADR-0015](../adr/0015-pack-asset-composition.md))、パックの中身([packs_pipeline.md](packs_pipeline.md))。

### 0.1 要求の確認

| 要求 | 意味 |
| --- | --- |
| FR-4.4 | リアルタイム情報は**サーバー側が保持**し、**LoRaWAN のダウンリンクとして端末へ届く** |
| FR-4.5 | 値はダミーでよい。ただし**サーバー上のシミュレータ**が生成し、**この配送経路を必ず通す**。端末内生成・HTTP 直接取得で代替しない |
| NFR-9 | 数十バイト級ペイロード・低頻度・**TTN フェアユース準拠** |

**「値は偽物でよいが、経路は本物」**([00_project.md](../00_project.md))がこの文書の全体を規定している。

## 1. 出発点 — 2 つの物理的制約が設計を決める

### 1.1 LoRaWAN Class A では、サーバーから任意のタイミングで送れない

**ダウンリンクは、端末がアップリンクを送った直後の受信ウィンドウ(RX1 / RX2)でしか届かない。**これは仕様であって実装の都合ではない。

したがって **「値が変わったらサーバーが push する」は原理的に作れない。**端末が聞きに行き、サーバーが答える形になる。

### 1.2 TTN フェアユースの下りは 1 日 10 通

| 制約 | 値 |
| --- | --- |
| アップリンクの電波占有時間 | **30 秒 / 日 / デバイス** |
| **ダウンリンクのメッセージ数** | **10 通 / 日 / デバイス** |
| AS923(日本)DR0〜DR2 のアプリケーションペイロード上限 | **51 バイト** |

**律速は下り 10 通である。**現行実装は**1 通で 1 スポットぶんしか返していない**ので、10 スポットで 1 日ぶんを使い切る。1 日 5〜8 か所を回りながら「昼に天気が変わったからもう一度聞く」ができない。

### 1.3 この 2 つから出てくる形

> **端末が「今のパックの全スポットぶんをください」と聞き、サーバーが 1 通で全部返す。**

これが [ADR-0016](../adr/0016-lora-terminal-driven-batch.md) である。20 スポットでも **22 バイト**なので 51 バイトに収まり、**1 日 10 通の予算で「朝・昼・夕 + 手動更新」が余裕を持って回る。**

## 2. ペイロード

### 2.1 アップリンク(端末 → サーバー)

```
バイト:  0        1            2
        ┌────────┬────────────┬──────────┐
        │ ver    │ pack_epoch │ cur_idx  │   = 3 バイト
        └────────┴────────────┴──────────┘
```

| フィールド | 意味 |
| --- | --- |
| `ver` | プロトコル版。**`0x01`** |
| `pack_epoch` | **端末が持っているパックの世代**(1 バイト)。パック生成時に採番([§4](#4-pack_epoch)) |
| `cur_idx` | 端末が今いると判断しているスポットの索引。**不明なら `0xFF`**。**サーバーの動作には影響しない**(ログ用) |

### 2.2 ダウンリンク(サーバー → 端末)

```
バイト:  0     1            2      3            2+N-1
        ┌─────┬────────────┬──────┬──────┬─────┬──────┐
        │ ver │ pack_epoch │code_0│code_1│ ... │code_N-1│   = 2 + N バイト
        └─────┴────────────┴──────┴──────┴─────┴──────┘
```

| フィールド | 意味 |
| --- | --- |
| `ver` | `0x01` |
| `pack_epoch` | **サーバーが返した世代。**要求と一致しなければ端末はコードを捨てる([§4](#4-pack_epoch)) |
| `code_i` | **上位 4 bit = 天気、下位 4 bit = 混雑。**`manifest.spots[i]` の順に並ぶ |

**索引を送らないのが要点である。**並び順が `manifest.spots` の順であると決めておけば、`spot_id` も索引も送らずに済む。20 スポットで 22 バイト。

### 2.3 コード値

| 値 | `weather` | `congestion` |
| --- | --- | --- |
| `0` | 晴れ | 空いている |
| `1` | 曇り | やや混雑 |
| `2` | 雨 | 混雑 |
| `0xF` | **不明** | **不明** |

- **`0xF`(不明)を必ず用意する。**値が無いことを表現できないと、旧実装のように**乱数で捏造する**([22 §6-2](../22_current_issues.md))か 0 で埋めるしかなくなる。`spot_realtime` の `NULL` がここに対応する
- 3〜14 は将来用に空けておく(4 bit ある)

### 2.4 端末はこのコードをどう使うか

[packs_pipeline.md §7.2](packs_pipeline.md) の `playback_rules` に従って variant を選ぶ。**対応表は manifest にデータとして入っている**ので、端末のコードに書かない。

```jsonc
"playback_rules": {
  "weather":    {"1": "weather_cloudy", "2": "weather_rain"},
  "congestion": {"1": "congestion_mid",  "2": "congestion_high"},
  "order": ["base", "weather", "congestion"]
}
```

`0` と `0xF` は表に無いので**該当 overlay を鳴らさない**(base だけ)。**天気と混雑は独立に効く**ので、雨かつ混雑なら 2 本続けて鳴る([ADR-0015](../adr/0015-pack-asset-composition.md))。

## 3. 配信スケジューラ

**フェアユースを守るのはサーバーの責任である。**端末側にも上限を置くが、**最後の砦はサーバー**に置く(端末は実験中に何度でも押される)。

| 規則 | 値 | 破ったときの挙動 |
| --- | --- | --- |
| デバイスあたりのダウンリンク | **10 通 / UTC 日** | **publish しない。**構造化ログに `downlink_budget_exceeded` を出す |
| 最短送信間隔 | **5 分** | 同上(`downlink_too_soon`) |
| 端末側の自動要求 | **90 分ごと** + 手動ボタン | 端末側で 1 日 8 回に自制する |

- **黙って落とさない。**「送ったつもりで届いていない」が最も分かりにくい失敗なので、必ずログに残す(P6)
- カウンタは**プロセス内ではなく DB に持つ**(`app.lora_downlinks`)。再起動でリセットされると上限の意味がなくなる

```sql
CREATE TABLE app.lora_downlinks (
  device_id  text NOT NULL,
  sent_date  date NOT NULL,              -- UTC
  count      integer NOT NULL DEFAULT 0,
  last_sent  timestamptz,
  PRIMARY KEY (device_id, sent_date)
);
```

## 4. `pack_epoch`

**端末が持っているパックと、サーバーが返すコード列の並びが一致していることを保証する 1 バイト。**

- パック生成時に採番する(`pack_jobs` に `epoch smallint` を持ち、ユーザーごとに 0..255 を巡回)
- manifest に `"pack_epoch": 7` として書く
- 端末はアップリンクにこの値を載せる
- **サーバーは、要求された `pack_epoch` が現在のパックと違えば、自分の `pack_epoch` を入れて `N=0`(コード無し)で返す**

端末は「並びが違う」ことを知り、**古いコードを新しいパックに当てはめる事故**を避けられる。**計画フェーズに戻ってパックを取り直すまで、リアルタイム反映は止まる**(これは正しい挙動である)。

## 5. サーバー側の構成

```
app/domains/realtime/
├── store.py       # spot_realtime の読み書き（値が無ければ unknown）
├── simulator.py   # シナリオの投入と進行（FR-4.5）
├── codec.py       # §2 のエンコード / デコード（純関数・テストしやすい）
├── scheduler.py   # §3 のフェアユース制御
└── mqtt.py        # TTN との MQTT（aiomqtt。lifespan で 1 つ）
```

### 5.1 MQTT クライアントは 1 プロセスに 1 つ

現行は `router.on_event("startup")` で **daemon スレッドを起こしている**([22 §6-8](../22_current_issues.md))。ワーカーを増やすと多重購読になり、ダウンリンクが重複する。停止イベントは誰も見ていない。

- **`app` の lifespan で 1 つだけ起動する**(aiomqtt、async)
- プロセス内キャッシュ `_state` は**持たない**。読むたびに DB を見る([22 §6-9](../22_current_issues.md) の無期限キャッシュを廃止)
- TTN のトピックは現行踏襲(`v3/{app_id}@ttn/devices/{device_id}/up` / `.../down/push`)

### 5.2 アップリンクの処理

```
uplink 受信
  └ frm_payload を base64 デコード → §2.1 で decode
     ├ ver が未知 → 無視してログ
     ├ device_id からユーザーと現在のパックを引く
     ├ pack_epoch 不一致 → N=0 の応答を作る（§4）
     ├ manifest.spots の順に spot_realtime を引き、code 列を作る（NULL は 0xF）
     └ scheduler が許せば publish、だめならログだけ（§3）
```

- **デコードした値を検証してから使う。**現行は base64 の中身を無検証で DB の upsert キーにしていた([22 §6-10](../22_current_issues.md))
- `device_id` とユーザーの対応は `app.users` に `lora_device_id text UNIQUE` を足して持つ(研究規模なので端末は数台)

## 6. シミュレータ(FR-4.5)

**「読み出し時に乱数で捏造して保存する」は廃止する**([22 §6-2](../22_current_issues.md))。値の出どころを明示的な第一級のコンポーネントにする。

### 6.1 シナリオ

```jsonc
// backend/data/scenarios/rainy_afternoon.json
{
  "name": "rainy_afternoon",
  "base_time": "2026-08-10T09:00:00+09:00",     // 相対時刻の起点
  "events": [
    {"at_min": 0,   "spot_id": "spot_007", "weather": 0, "congestion": 1},
    {"at_min": 180, "spot_id": "spot_007", "weather": 2, "congestion": 2},
    {"at_min": 180, "spot_id": "spot_012", "weather": 2, "congestion": 0}
  ]
}
```

```
python -m app.cli rt-load    <scenario.json>     # 投入（events を DB に置く）
python -m app.cli rt-start   [--speed 60]        # 進行開始（--speed は実時間倍率)
python -m app.cli rt-stop
python -m app.cli rt-set     <spot_id> --weather 2 --congestion 1   # 手で 1 点だけ変える
python -m app.cli rt-show                                           # 現在値の一覧
```

- **`source` 列に `simulated` を必ず記録する**([data_model.md §4.7](data_model.md))。実センサ由来と混ざらない
- 進行は `app` 内の asyncio タスク。`--speed 60` なら 1 分が 1 秒で進む(実験の再現に要る)
- **シナリオに無いスポットは `NULL`(unknown)のまま。**埋めない

### 6.2 管理 API(計画フェーズの UI から触る用)

```http
POST /api/v1/realtime/simulator/{action}    # load | start | stop
POST /api/v1/realtime/spots/{spot_id}       # 1 点だけ手で設定
```

旧 `POST /realtime/_mock/{spot_id}` の置き換え。**CLI と同じ処理を呼ぶだけ**にして、2 系統の実装を作らない。

## 7. HTTP は計画フェーズ専用

| フェーズ | 経路 |
| --- | --- |
| **計画フェーズ**(オンライン) | `GET /api/v1/realtime/spots/{spot_id}`(ETag 対応。[chat_sse.md §3.3](../40_api/chat_sse.md)) |
| **観光フェーズ**(オフライン) | **LoRaWAN のみ。**HTTP は使わない(FR-4.5) |

**これは実装の分岐ではなく、端末の状態の問題である。**観光フェーズでは通信そのものが無いので HTTP は失敗する。**「実験のときだけ HTTP で取る」抜け道を作らない**ことが FR-4.5 の要求であり、端末側の実装([offline_field_mode.md §5](offline_field_mode.md))でも観光モードでは HTTP を呼ばない。

## 8. 縮退(NFR-5)

| 事象 | 挙動 |
| --- | --- |
| LoRa 未接続 / Join 失敗 | **端末は `base` だけを鳴らす。**案内は成立する。画面に「リアルタイム情報なし」と出す |
| ダウンリンクが来ない(予算超過・電波) | 同上。**前回受け取ったコードを使い続ける**(時刻とともに表示する) |
| `pack_epoch` 不一致 | コードを捨てて `base` のみ。「パックが古い」と表示 |
| MQTT ブローカー断 | アップリンクが届かない。サーバー側はログのみ。**対話・パック生成には影響しない** |
| シミュレータ未起動 | 全スポット `unknown`(`0xF`)。**捏造しない** |

**リアルタイム情報は「あれば案内が良くなる」ものであって、無いと案内が止まるものではない。**この位置づけを崩さない(P5)。

## 9. 端末側に必要な変更(最小)

> 詳細は [frontend_nav.md §4](frontend_nav.md)。**現行の `loraBridge.js` はそのまま使う。**

| ファイル | 変更 |
| --- | --- |
| `src/lib/loraBridge.js` | 受信の `JSON.parse(...)` を **§2.2 のバイナリ decode に差し替える**(1 関数・約 15 行)。AT コマンド・Join・Android ブリッジの部分は**触らない** |
| `src/stores/rt.js` | `processRtDoc(json)` を `applyDownlink(bytes, manifest)` に置き換える。HTTP ポーリングは**計画フェーズ専用**として残す |

## 10. 決定の記録(2026-08-01)

| # | 決定 | 根拠 |
| --- | --- | --- |
| 1 | **端末駆動の request/response にする** | LoRaWAN Class A ではダウンリンクは uplink 直後の RX ウィンドウでしか届かない。**サーバー push は原理的に作れない** |
| 2 | **1 通のダウンリンクでパックの全スポットを返す** | 律速は**下り 10 通 / 日**。1 スポット 1 通では 10 か所で使い切る |
| 3 | **索引を送らず `manifest.spots` の順に並べる** | 20 スポットで 22 バイト。51 バイト(AS923 DR0〜DR2)に収まる |
| 4 | **1 バイトに天気 4 bit + 混雑 4 bit** | 2 つは独立した軸([ADR-0015](../adr/0015-pack-asset-composition.md))。`0xF` を「不明」に割り当てる |
| 5 | **`0xF`(不明)を必ず持つ** | 値が無いことを表現できないと捏造するしかなくなる([22 §6-2](../22_current_issues.md)) |
| 6 | **`pack_epoch` で並びの一致を保証する** | 古いコードを新しいパックに当てはめる事故を防ぐ |
| 7 | **フェアユースの上限はサーバーが持ち、DB に数える** | プロセス内カウンタは再起動でリセットされ、上限の意味がなくなる |
| 8 | **超過時は publish せずログに出す** | 「送ったつもりで届いていない」を見えるようにする |
| 9 | **MQTT は lifespan で 1 つ。プロセス内キャッシュを持たない** | 多重購読とダウンリンク重複([22 §6-8](../22_current_issues.md))、無期限キャッシュ([22 §6-9](../22_current_issues.md))の解消 |
| 10 | **シミュレータをシナリオ + CLI で第一級にする** | FR-4.5。読み出し時の乱数捏造を廃止する |
| 11 | **HTTP は計画フェーズ専用** | FR-4.5。実験時の抜け道を作らない |
| 12 | **リアルタイム情報が無くても案内は成立する** | P5。`base` だけ鳴らす |
| 13 | **端末側の変更は decode 部分だけ** | ユーザー指示(2026-08-01)。AT コマンド・Join の実装は動いているものを触らない |

## 11. 採らなかった案

| 案 | 不採用の理由 |
| --- | --- |
| サーバーからの push(値が変わったら送る) | **Class A では不可能。**Class C は端末の消費電力が現実的でない |
| 1 スポット 1 ダウンリンク(現行方式) | 下り 10 通 / 日で 10 スポット。1 日ぶんの行程で使い切る |
| JSON をそのまま載せる(現行方式) | `{"s":"spot_012","w":1,"c":2}` で 27 バイト。**1 スポットで**この量になり、全スポットを 1 通に入れられない |
| `spot_id` を文字列で載せる | 8 バイト × N。索引順で並べれば 0 バイトで済む |
| 差分だけ送る(変わったスポットのみ) | 端末が前回値を持っている前提が要る。**取りこぼすと恒久的にずれる。**全部送っても 22 バイト |
| ACK・再送 | 次の要求で取り直せば済む。フェアユースの予算を再送に使うほうが損 |
| 予報(`u` / `h`)を載せる | **供給源がサーバーに無い**([22 §12-4](../22_current_issues.md) のデッド UI)。作るなら別の要求として立てる |
| 実験時だけ HTTP で取得 | FR-4.5 が明示的に禁じている |

## 12. 実装時に決めること(設計判断ではない)

| # | 項目 |
| --- | --- |
| 1 | 端末の自動要求間隔(90 分)と 1 日の自制回数(8 回) |
| 2 | 最短送信間隔(5 分) |
| 3 | シミュレータの `--speed` の既定値 |
| 4 | `device_id` とユーザーの紐づけ手順(研究用に手作業でよい) |
| 5 | f_port の値(現行の `2` を踏襲する) |
