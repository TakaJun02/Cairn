# ADR-0010: `understand` を「ask_user と done の 2 Tool だけを持つ有界エージェント」にする

> **⚠ この ADR は [ADR-0018](0018-ask-user-resumable-tool.md) によって置き換えられた (superseded by ADR-0018、2026-08-03)。**
>
> **本 ADR の中心的な根拠が成立していなかった。**「参照が解けていないと妥当な plan を書けないので聞き返しを Tool にできない」(下記「理由」1)としたが、**そのときの plan は `[ask_user]` の 1 手だけでよく、前段の手を書かせる必要はなかった。**
>
> 現在は **`ask_user` は結果を返す 1 つの Tool** に統合され、ターンの中断・復帰で実現される。本 ADR が導入した `action`/`clarify` フィールド・辺 E6・ガードレール G6〜G9・`respond` の「聞き返し」モードは**すべて廃止または統合された。**以下は記録として残す。

- 状態: **廃止 (superseded by [ADR-0018](0018-ask-user-resumable-tool.md))**
- 日付: 2026-07-31(廃止 2026-08-03)
- 関係: [ADR-0008](0008-plan-then-execute.md)(一括プラン方式)を**置き換えない。**`understand` ノードの内側にだけ 2 択の分岐を足す / [ADR-0007](0007-preference-elicitation.md)(選好の引き出し)とは**別の種類の質問**を扱う

## 文脈(何が問題か)

本システムの設計は、LLM が正しく判別できないことを前提に、多くの安全装置を積んでいる。

- 出力スキーマを guided decoding で強制する
- `spot_id` を「文脈上参照可能な id」だけの enum に絞る
- 生成された `spot_id` を DB と `last_candidates` に照合する
- 述語と引数の実在を検査し、未知のものは `unmodeled` に落とす
- plan を P1〜P8 で検証し、不正な手を破棄する

**しかしこれらはすべて「LLM が間違えたら、間違いを検出して落とす」方向の対処である。**落とした結果ユーザーに返るのは「どれのことか分かりませんでした」「〇〇は飛ばしました」という**事後報告**で、ユーザーは要求を打ち直すことになる。

とりわけ深刻なのが**照応の曖昧さ**である。[30_design/agent_planning_phase.md §3.3](../30_design/agent_planning_phase.md) が指摘するとおり、序数の取り違えは**静かに間違った POI を旅程に入れる**という気づきにくい失敗を生む。「2 番目のやつを外して」に対して候補が 2 つあるとき、現行設計にできるのは「破棄して謝る」か「賭ける」かのどちらかしかない。

**第 3 の選択肢がある — 聞き返すこと。**ところが現行の `ask_user` Tool は選好の聞き取り(ADR-0007)専用で、しかも `act` が plan に従って実行するものである。**参照が解けていない状態では、そもそも妥当な plan を書けない。**

## 決定(何をすると決めたか)

**`understand` ノードに `ask_user` と `done` の 2 つだけを与え、どちらかを選ばせる。**

- **`done`** — 抽出結果 + `intent` + `plan` を出す。以降は従来どおり `validate_plan` → `act` → `respond`
- **`ask_user`** — **`plan` を出さず**、曖昧さと 2〜4 個の選択肢を出す。`validate_plan` と `act` を飛ばして `respond` が質問文を書く

出力スキーマでは `action: "done" | "ask_user"` の分岐として表現し、**`action` は抽出フィールドより後ろに置く**(進めるかどうかは抽出をやってみて初めて分かるため)。

**`act` が持つ `ask_user` Tool はそのまま残す。**こちらは選好の聞き取り専用で、動機も置かれる層も違う。

| | **`understand` の `ask_user`(本 ADR)** | **`act` の `ask_user` Tool(ADR-0007)** |
| --- | --- | --- |
| 何を聞くか | **言われたことの意味**(「『2 番目』はどちらですか」) | **ユーザーの選好**(「どなたと行かれますか」) |
| 動機 | **反応的**(発話に実際にあった曖昧さ) | **能動的**(こちらから聞きに行く) |
| 出すもの | 曖昧さ + 具体値に解決できる選択肢 | スロット + 選択肢 |
| ガードレール | **G6〜G9** | G1〜G5 |
| 質問だけで返してよいか | **よい**(進めないので) | **だめ**(G4) |

**ガードレール(コードで強制する)**

| # | 規則 |
| --- | --- |
| G6 | **選択肢を 2〜4 個「具体的に」列挙できないなら聞き返さない。**`spot_id` は DB 照合、解釈は enum 照合。通らなければ強制的に `done` 扱い |
| G7 | **同じ曖昧さを 2 回聞かない**(`resolved_ambiguities`) |
| G8 | **連続する聞き返しは 1 ターンまで。**2 ターン続いたら最も確からしい解釈を採り、仮定を明示する |
| G9 | **妥当な plan を出せるなら聞き返さない**(「念のため確認」の禁止) |

**聞き返しの答えを元の要求に結びつける。**曖昧だった表層形・選択肢・元の発話を `pending_clarification` としてスレッドに 1 ターンだけ残し、次のターンのプロンプトに載せる。**pending な plan を保存して再開する仕組みは作らない** — 状態は毎ターン DB から再構築する原則を崩さないため。

## 理由(なぜ他案でなくこれか)

**1. 聞き返しを Tool として plan に置く案は、筋が通らない。**参照が解けていないのに前段の手を組み立てさせ、最後に「ところで、どれのことですか」と付ける形になる。**理解できていないなら、理解できていないと言うのが先**である。またこの案だと `ask_user` Tool の意味が 2 つに割れ、P5・P6 の検証規則も増える。

**2. 判断する場所として `understand` が正しい。**何が曖昧だったかを知っているのは `understand` だけである。`act` は渡された plan を実行するだけで、その plan がどれだけ怪しい推測の上に建っているかを知らない。

**3. ADR-0008 が退けたものとは別物である。**同 ADR が退けたのは「毎周 LLM が次の手を判断する多段の自律ループ」で、理由はレイテンシが読めないこと(NFR-3)と 31B の多段自律判断が失敗域にあることだった。本件は:

- **LLM 呼び出しが増えない。**どちらの分岐でも `understand` は 1 回。ターン合計も 2〜3 回のまま
- **ターン内にループがない。**次の観測(ユーザーの答え)はターンを終えないと得られないので、**1 ターン 1 ステップで構造的に確定する**
- **判断は 2 択 1 回だけ。**多段推論を要求していない
- グラフの巡回は増えない。増えるのは `understand` → `respond` の**片道の近道の辺 1 本**だけ

**4. ユーザーの手間が減る。**「分かりませんでした」と言われて全文を打ち直すより、チップを 1 タップするほうが速い。JR 東日本が実証を経てチャットから選択式に転換した知見([30_design/recommendation_planning.md §2.3(c)](../30_design/recommendation_planning.md))と同じ方向である。

**5. 採らなかった代替案**

| 案 | 不採用の理由 |
| --- | --- |
| 現状維持(破棄して事後報告) | 照応の取り違えに対して「賭ける」か「謝る」しかない。静かな失敗が残る |
| 聞き返しを `act` の Tool にする | 上記 1・2 |
| 確信度スコアを出させて閾値で判定 | 較正されていない自己申告確信度に閾値を置くと、モデル・プロンプト変更のたびに再調整が要る。**「選択肢を具体的に 2〜4 個出せるか」のほうが検査しやすく、意味も明快** |
| `understand` に検索 Tool も持たせる(本物の ReAct) | ターン内で複数回 LLM を回すことになり、ADR-0008 の懸念に正面から当たる |

## 影響(この決定で生じる制約・やること)

- **出力スキーマに `action` と `clarify` が加わる**([30_design/agent_planning_phase.md §3.1](../30_design/agent_planning_phase.md))
- **スレッド状態が 3 つ増える**: `pending_clarification`(1 ターン限り)/ `resolved_ambiguities` / `clarify_streak`。**`data_model.md` に反映が要る**
- **グラフに辺 E6 が増える**(`understand` → `respond`)。`validate_plan` と `act` を飛ばす経路が正式に存在することになる
- **`respond` に「聞き返し」モードが増える**(計 4 モード)
- **`understand_action` を構造化ログに出す**(2026-08-01 改訂: 旧「`turn_metrics` に聞き返し率を記録して監視する」。NFR-7 の削除により計測テーブルを持たないため、**聞きすぎているかは実際に使って判断する**ことになった)
- **層 1 自動テストに G6〜G9 を追加する**
- **最大のリスクは「聞きすぎ」。**LLM の棄権能力は問題種別に依存し、強い指示を与えると答えられる問いまで棄権する方向に振れることが報告されている(COLING 2025)。**G6〜G9 は抑制だが、効いているかは計測でしか分からない。**聞き返し率が高すぎるなら G9 の判定を厳しくする
