# ADR-0007: 選好の引き出しは「初回は選択式、追加質問は ask_user ツール」とし、質問回数はコードで縛る

- 状態: 承認 (2026-07-30、ユーザーが [30_design/recommendation_planning.md](../30_design/recommendation_planning.md) §8 の論点 6 に回答)
- 日付: 2026-07-30

## 文脈(何が問題か)

FR-1.1 は「対話からプロファイルを獲得する」ことを求め、FR-3.2 は「自然言語で完結できる」ことを求める。この 2 つは素直に実装すると衝突する — プロファイルを埋めるために質問を重ねると、対話が**尋問**になる。

外部の証拠が両方向にある。

- LLM 型 CRS(対話推薦システム)の系統的レビューは**冗長性が主要な UX 課題**だと指摘している
- **JR 東日本は実証を経て、自由チャット形式から選択式へ転換した** — 実サービスが実際に踏んだ判断である
- 一方 COPE (SIGIR 2026) は「最適な引き出しは段階依存で、**序盤は属性ベースの質問、選好が固まればアイテム提示が優位**」と報告している。つまり序盤に質問することそれ自体は正しい

また、主要スロット(party / mobility / interests)が空のまま推薦すると的外れになるが、埋まるまで推薦を止めると「聞かれるばかりで何も出てこない」体験になる。

## 決定(何をすると決めたか)

1. **初回の聞き取りは選択式**(クイックリプライのチップ)とする。party / mobility / interests を 2〜3 タップで埋める
2. **追加質問は ReAct 型の `ask_user` ツール**として実装する。`act` が持つツール集合(`recommend` / `plan_itinerary` / `edit_itinerary` / `answer_qa` / `ask_user`)に並べ、`understand` が `next_action` として選ぶ
3. **初回聞き取りも `slot: "onboarding"` の `ask_user` 呼び出しとして表現し、専用パスを作らない**
4. **質問の回数と条件はコードで強制する。**LLM の裁量に任せない:

   | # | 規則 | 実装 |
   | --- | --- | --- |
   | G1 | 1 ターン 1 問まで | `act` が 2 個目以降の `ask_user` を破棄 |
   | G2 | 同じスロットを 2 回聞かない | `asked_slots` をスレッド状態に持ち、既出スロットの `ask_user` を破棄 |
   | G3 | `ask_user` 単独で終われるのは連続 2 ターンまで | 3 ターン目は強制的に「仮定明示 + 推薦」へ切り替え(`ask_user` を無効化) |
   | G4 | 推薦要求に対して `ask_user` 単独を返さない | 主要スロットが**全部**空の初回だけ例外。それ以外は「仮定を明示した推薦 + 確認質問 1 つ」を同時に返す |
   | G5 | 選択肢は 2〜4 個 + 自由入力を常に残す | チップは提案であって強制ではない |

5. **`ask_user` は `state: ask_user(options)` を送出し、UI がチップを描画する。**質問文の日本語は `respond` が生成する

## 理由(なぜ他案でなくこれか)

- **`ask_user` をツールとして置くことで、質問が特別扱いでなくなる。**「推薦する」「旅程を作る」「質問する」が同じ層の選択肢になるので、分岐が増えず、初回オンボーディングも同じ経路を通る(専用フローを持たない)
- **LLM 呼び出しは増えない。**`ask_user` は `act` のツール実行が「質問を組み立てる」に置き換わるだけで、`understand` → `act` → `respond` の 2 呼び出し構成([ADR-0004](0004-conversation-pipeline.md))を保つ
- **ガードレールをコードに置く理由は、LLM に任せると際限なく質問するから。**冗長性が UX 課題だという系統的レビューの指摘と、JR 東日本が自由チャットを捨てた事実の両方が、これを裁量に任せてはいけないことを示している。プロンプトで「聞きすぎないで」と書く方式は検証できない
- **G3 と G4 は別の穴を閉じている。**G4 は「質問だけで手ぶらに帰さない」、G3 は「質問が続く場合の打ち切り」。**両方あって初めて「聞かなすぎ」と「聞きすぎ」の両側が閉じる**
- **選択式を全面採用しない(G5 で自由入力を残す)のは FR-3.2 との両立のため。**JR 東日本の転換は「選択式の方が良い」ことの証拠だが、本件は自然言語で完結できることを要求として持っている。チップを**提案**に留めれば両立する
- **G4 の「仮定明示 + 推薦」は COPE の段階依存性に沿う。**序盤は属性の質問が有効だが、それは「質問だけを返す」ことを意味しない。仮定を明示した推薦を添えれば、ユーザーは選択肢を見ながら選好を言語化できる(アイテム提示による引き出し)

## 影響(この決定で生じる制約・やること)

- **`asked_slots` をスレッド状態に追加**する(G2 の実装に必要)
- **連続 `ask_user` のカウンタをスレッド状態に持つ**(G3)
- **`understand` の出力スキーマに `next_action`(ツール名の enum)を追加**する
- UI に**クイックリプライのチップ**コンポーネントが必要になる。`state: ask_user` を受けて描画し、タップで送信、自由入力も可能なままにする
- **`ask_user` の縮退経路(G3 の打ち切り)をシナリオ回帰の台本に含める**([30_design/recommendation_planning.md](../30_design/recommendation_planning.md) §7 層 2)
- プロファイルのチップ列表示([ADR-0006](0006-recommendation-hybrid.md))と組み合わせ、**「今システムが把握していること」が常に画面上で見える**状態にする。質問が減ってもユーザーが不安にならないための条件
