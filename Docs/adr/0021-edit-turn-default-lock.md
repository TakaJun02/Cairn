# ADR-0021: 編集ターンでは訪問集合を既定で固定し、再充填は明示要求があるときだけ行う

- 状態: **提案(2026-08-04)**
- 日付: 2026-08-04
- 関係: [ADR-0005](0005-itinerary-solver.md) 系(自作 ILS)の**目的関数の運用を編集ターンについて改める** / [recommendation_planning.md §4.5](../30_design/recommendation_planning.md) / [agent_react_architecture.md §5](../30_design/agent_react_architecture.md) / [25_known_issues.md §1-2](../25_known_issues.md)

## 文脈(何が問題か)

「三崎公園は外して」という 1 件の削除依頼に対し、三崎公園に加えて**牛渡川も外れ、奈曽の白滝・金峰神社が入った**(2026-08-04 実機。[25_known_issues.md §1-2](../25_known_issues.md))。diff カードには正直に出るが、ユーザーは 1 件の削除しか頼んでいない。

原因は目的関数の構造にある。編集の安定性は「β × 編集距離」の減点(β=0.6)だけで担保しているが、**β は効用 1 件分より小さい**。削除で空いた時間に別スポットを詰め直す(再充填)と、効用の増分が編集距離ペナルティを容易に上回るため、ILS は毎回「効用最大の再充填」を選ぶ。これは §4.2 で退けた「1 つ足してと言うと全部組み替える」失敗(Flex-TravelPlanner / TripTide)の縮小再生産である。

検討した対処は 3 案:

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A. 既定固定 + 再充填フラグ【採用】** | 編集ターンでは既存訪問の削除と新規スポットの自動挿入を止め、変更は ops によるものだけにする。再充填は明示要求があるときだけ | 挙動が予測可能。説明も単純(「頼まれたことだけやる」) |
| B. 編集ターンだけ β を強める | ソフトな抑制 | 効用差が大きいと依然入れ替えが起きる。βの調整合戦になる |
| C. 入れ替えが起きたら respond で確認 | 再充填は維持し HITL で確認 | 往復が 1 回増える。「そもそも頼んでいない」ことに変わりがない |

**2026-08-04、ユーザーと協議のうえ A を採用した。**

## 決定(何をすると決めたか)

### 1. 編集ターンの既定挙動: 訪問集合の変更は ops によるものだけ

- `edit_itinerary` では、ops 適用後の訪問集合を**ソルバーの操作から保護する**: shake による削除の対象にせず、**新規スポットの挿入候補を空にする**
- **実装注記の訂正(2026-08-04 レビュー指摘)**: 当初この削除保護に既存の `protected_spot_ids` を充てると書いたが、ソルバー実装上この集合は 2-opt / or-opt / shake すべてを止める「不動」の意味を持ち、流用すると並び替えまで固定される(下の「採らなかった案」の挙動そのもの)。**削除保護専用の集合(`removal_protected_spot_ids`)を新設し、shake / 実行可能化(`_make_feasible`)だけがそれを見る。並び替え(2-opt / or-opt)は従来どおり `locked` だけが制限する**
- ソルバーがやるのは**並び・時刻の再調整と経路の引き直しだけ**になる。新しい制約(例: 「午前はゆっくり」)が訪問集合を変えないと満たせない場合は、**スポットを勝手に落とすのではなく譲歩(Concession)として報告する**。respond が「◯◯を外せば守れます」と提案し、ユーザーが次のターンで決める
- **例外(2026-08-04 明記)**: 時間割が物理的に組めない場合(例: `set_time` で 1 日に収まらなくなった)の実行可能化フォールバックによる削除だけは残る。この削除は diff(`removed`)に現れ respond が言及するが、譲歩(Concession)としての構造化報告は将来課題([90_backlog](../90_backlog.md))
- `plan_itinerary`(新規作成)は従来どおりフル ILS(この問題は編集の安定性の問題であり、初回構築には当たらない)

### 2. 再充填フラグ `allow_refill`

- `edit_itinerary` の引数に **`allow_refill: bool`(既定 false)**を追加する
- メインエージェントは、**ユーザーが補充・入れ替えを明示的に求めたときだけ** true にする(例: 「代わりにどこか入れて」「空いた時間に何か足して」「もっと良い組み合わせにして」)
- `allow_refill: true` のときは従来どおりフル ILS(β × 編集距離の減点も従来どおり効かせる)

### 3. 解の多様化と LLM 選択は再充填時だけ

- 既定(集合固定)では解は並びと時刻しか変わらないため、**解 A/B/C の生成と LLM による選択(1 回)を省略**し、単一解を返す。編集ターンの LLM 呼び出しが 1 回減る
- `allow_refill: true` のときは従来どおり A/B/C + 選択

## 採らなかった案

- **B(β 強化)**: 上表のとおり。なお β=0.6 自体は `allow_refill: true` の経路では引き続き使う(強めるかは実測後の調整項目)
- **C(respond で確認)**: 上表のとおり
- **全項目 `locked` 扱いにする**: `locked` は相対順序まで固定する意味を既に持っている(ユーザーの「ここは動かさないで」)。既定固定は「集合は変えないが、並び・時刻の再調整は許す」であり、意味が異なる。**削除保護専用の集合(`removal_protected_spot_ids`。上記の実装注記)**と挿入候補の制限で表現し、`locked` の意味は変えない

## 帰結

- 「外して」は外すだけ、「足して」は足すだけになる。**diff がユーザーの依頼と 1:1 に対応する**
- 空いた時間は空いたまま返る。埋めたければユーザーが頼む(そのときの diff も明示要求由来)
- 制約とのトレードオフは譲歩として可視化され、勝手な解決をしない([ADR-0005](0005-itinerary-solver.md) の「無言破棄の禁止」と同じ思想)
- メインエージェントのプロンプトに `allow_refill` の判断基準(明示要求の例)を足す必要がある([agent_react_architecture.md §5](../30_design/agent_react_architecture.md))
