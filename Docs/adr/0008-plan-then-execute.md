# ADR-0008: エージェントの制御構造は一括プラン方式(Plan-then-Execute)にする

- 状態: 承認 (2026-07-31、ユーザー判断)
- 日付: 2026-07-31
- 関係: [ADR-0004](0004-conversation-pipeline.md) を**置き換えず、`act` の内側を詳細化する**

## 文脈(何が問題か)

[ADR-0004](0004-conversation-pipeline.md) は対話ターンを `load_context → understand → act → respond → persist` と定めたが、**`act` が 1 ターンに何をどれだけ実行するか**は決めていなかった。

方式決定([ADR-0005](0005-itinerary-solver.md) / [ADR-0006](0006-recommendation-hybrid.md) / [ADR-0007](0007-preference-elicitation.md))によって `act` の道具が 5 つに増えたことで、この未決が実際の問題になった。ユーザーの発話は**複数の道具をまたぐことが普通にある**:

> 「明日は滝を 2 つ入れて、宿の近くで昼を取れるようにして」
> → `recommend`(滝を 2 つ選ぶ)+ `edit_itinerary`(旅程に入れて再最適化)

1 ターン 1 道具に固定すると、これが 2 ターンに分かれる。ユーザーは「滝を 2 つ」と言ったのに候補が出てくるだけで、もう一度「それを入れて」と言う必要がある。

同時に、`gemma-4-31B` に多段の自律判断をさせることには根拠のある不安がある。TravelPlanner 系のベンチマークで、素の Qwen3-32B(本件に最も近いモデルクラス)は成功率 0.6% であり、**多段の計画立案そのものがこのクラスの弱点**である([30_design/recommendation_planning.md](../30_design/recommendation_planning.md) §2.2)。

## 決定(何をすると決めたか)

**一括プラン方式(Plan-then-Execute)を採る。**

1. **`understand` が「使う道具の列」を 1 回の JSON 出力で決める**(`plan: [{id, tool, args}, ...]`)。コードがそれを順に実行する
2. **手は最大 3 つ。**LLM 呼び出しは 1 ターン 2〜3 回で固定のまま
3. **ステップ参照 `$N` を導入する。**後の手が前の手の結果を参照できる記法(`$1.spot_ids`、`$1.spot_ids[:k]`、`$N.itinerary` の 3 つのみ)。**コードが解決し、LLM 呼び出しは発生しない**
4. **plan は実行前にコードで検証する**(P1〜P8)。手数上限・道具名の enum・引数スキーマ・前方参照のみ・`ask_user` は末尾のみ・旅程を書き換える手は 1 つまで・追加 LLM 呼び出しは 1 回まで
5. **`state: plan` イベントを最初に送出する。**「今から何をするか」を応答生成の前に提示する
6. **手 k が失敗したら残りは実行しない**が、そこまでの結果は捨てない。DB への書き込みは全手完了後の 1 トランザクション
7. **破棄・失敗した手は握り潰さず** `respond` に渡し、構造化ログに出す

## 理由(なぜ他案でなくこれか)

- **複合要求を 1 ターンで捌けて、しかも LLM 呼び出し数が増えない。**これが決め手である。案 A(1 ターン 1 道具)は最も単純だが、上記の「滝を 2 つ入れて」が 2 ターンに割れる。案 C(有界 ReAct ループ)は 1 ターンで捌けるが呼び出しが 3〜6 回に増える
- **レイテンシが読める(NFR-3)。**呼び出し数が固定なので、TTFT とターン全体の所要時間が事前に見積もれる。ReAct ループはループ回数が入力依存なので読めない
- **31B に多段の自律判断をさせない。**案 C は「道具の結果を見て次を決める」判断を毎周 LLM に求める。これは TravelPlanner 系で 0.6% 台の失敗を出しているモデルクラスの弱点そのものである。一括プランなら**判断は 1 回だけ**で、しかもその 1 回はコードで検証できる(P1〜P8)
- **何が起きたのか追いやすい。**「何をしようとして、何が破棄されたか」がターン 1 行のログに収まる。ReAct ループでは軌跡が可変長になり、読むのも比べるのも難しい
- **`state: plan` の先出しが UX 上効く。**一括プランは実行前に全体の段取りが確定しているので、「推薦して、旅程に入れます」を LLM の応答を待たずに表示できる。ReAct ループではこれができない(次に何をするかがまだ決まっていない)
- **受け入れる代償を明示する: 道具の結果を見て次の道具を選べない。**「推薦結果を眺めてから良さそうなものを旅程に入れる」という適応的な段取りができない。**ステップ参照 `$N` がこれを部分的に埋める** — 値を見られなくても「手 1 の結果を手 2 に渡す」と書けるので、複合要求の大半は通る。それでも足りないケース(結果の中身次第で分岐したい)は 2 ターンに分かれるが、これは案 A の常態にすぎず、後退ではない

## 影響(この決定で生じる制約・やること)

- **`understand` の出力スキーマに `plan` を追加**する。道具名と引数は guided decoding の enum + スキーマで縛る([30_design/agent_planning_phase.md](../30_design/agent_planning_phase.md) §3)
- **plan の検証器(P1〜P8)とステップ参照の解決器**が新しいモジュールとして必要になる(`domains/conversation/planner.py`)
- **追加 LLM 呼び出しの割り当て規則**が必要になる: 他の手から参照されている手を優先 → 複数なら最も早い手 → 参照がなければ最後の手。割り当てられなかった手は決定的な結果を使う(縮退)
- **`state: plan` イベントをフロントが解釈する**必要がある。「これから何をするか」の表示コンポーネントが要る
- **破棄した手と理由を構造化ログに出す。**プロンプトを直すときの主シグナルになる
- ステップ参照の語彙を増やすときは[30_design/agent_planning_phase.md](../30_design/agent_planning_phase.md) §1.2 を先に更新する(Docs 駆動開発)
- [ADR-0004](0004-conversation-pipeline.md) は有効なまま。本 ADR はその `act` を詳細化するもので、パイプラインの 5 段構成は変えない
