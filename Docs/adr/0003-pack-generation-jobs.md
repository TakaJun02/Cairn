# ADR-0003: パック生成をDBジョブ+プロセス内asyncioワーカーで非同期化する(Celery/Redisは再導入しない)

- 状態: 提案
- 日付: 2026-07-29

## 文脈(何が問題か)

パック生成(スポット×状況ぶんのナレーションLLM生成+TTS+ファイル書き出し)は分単位のバッチ処理だが、現行は `POST /api/nav/plan` の同期HTTPリクエスト内で完結し、タイムアウトはハードコード3000秒。TTS 1件の失敗で全体が500になり、書き込み済みファイルは孤児化し、再試行のたび新しいpack_idでディスクに積み上がる([22 §2](../22_current_issues.md))。過去にCelery+Redisの非同期構成があったが2026-07に廃止されており、`run_nav_test.sh` など当時の残骸が現行APIと不整合のまま残っている。

## 決定(何をすると決めたか)

パック生成をジョブとしてモデル化する:

- `pack_jobs` / `pack_assets` テーブルで状態管理(`queued → running → ready | partial | failed`、アセット単位の部分成功)
- `POST /api/v1/packs` は 202 + `job_id` を即時返却、`GET /api/v1/jobs/{id}` で進捗取得
- 実行は `app` プロセス内のasyncioワーカー(lifespanで起動)。ナレーションはSemaphore(8)並列、TTSはSemaphore(3)+指数バックオフ
- 冪等性: 同一パラメータの再要求は既存ジョブ/パックを返す
- Celery/Redis等の外部ジョブ基盤は導入しない

## 理由(なぜ他案でなくこれか)

- HTTP同期のままでは、ブラウザ・Gateway・下流の全タイムアウトを50分に引き伸ばす歪みが残り、進捗表示も部分再開も原理的にできない
- Celery/Redisはワーカープロセス・ブローカー運用・シリアライズ制約が増え、実験規模(同時ジョブ数個)に見合わない。一度廃止した経緯とも整合
- DBジョブテーブルなら再起動後の再開(`running`を`queued`に戻す)・履歴の実験データ化(所要時間の記録)が自然に手に入る

## 影響(この決定で生じる制約・やること)

- フロントにジョブ進捗UI(ポーリングまたはSSE)を実装する
- appプロセス再起動時の実行中ジョブ回復ロジックが必要
- スループット上限はappプロセス1つぶん。将来必要になれば同一コードベースのワーカー専用プロセスを増やせる設計(ジョブ取得をSELECT ... FOR UPDATE SKIP LOCKEDに)としておく
