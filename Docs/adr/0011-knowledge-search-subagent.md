# ADR-0011: 知識検索を独立したサブエージェント(Agent as a Tool)として切り出す

- 状態: **承認 (2026-08-01、ユーザー指示)**
- 日付: 2026-08-01
- 関係: **[ADR-0009](0009-no-subagents.md)(サブエージェントを持たない)の適用範囲を限定する。**同 ADR が自ら定めた「覆す条件」に該当したため / [ADR-0008](0008-plan-then-execute.md)(一括プラン方式)は**メインエージェントについては維持** / 方式は [ADR-0012](0012-knowledge-retrieval-pgvector.md)
- 設計: [30_design/narration_qa.md](../30_design/narration_qa.md)

## 文脈(何が問題か)

`answer_qa` は「知識ベースを引いて抜粋を返すだけ」の単純な Tool として設計されていた([30_design/agent_planning_phase.md §19.3](../30_design/agent_planning_phase.md))。しかし実データを測ると、これでは足りないことが分かった。

**1. 検索は 1 回で当たらない。**知識 MD 118 本を `##` 見出しで割ると、`## 概要` が **115 ファイル**、`## アクセス` が **58 ファイル**に現れる。ほぼ同型のチャンクが大量に競合するので、「1 回引いて上位 k 件を返す」では取りこぼす。実際に必要なのは **「引く → 足りない → 語を変えて引き直す → 断片が切れている → 全文を取る」**という反復である。

**2. その反復の中間状態は、メインのコンテキストに置けない。**メインエージェントは `max_model_len` **16,384** の中で、プロファイル・制約・会話履歴・spot 語彙・plan を扱っている([同 §7](../30_design/agent_planning_phase.md) で入力約 7,000 を積んである)。ここに検索の観測履歴・全文チャンク・Web の本文が積み上がる余地はない。

**3. 検索の専門性がメインの Tool 選択に混ざる。**意味検索・字句検索・全文取得・Web 検索の 4 つをメインの Tool メニューに並べると、メインは「推薦するか旅程を編集するか」と「どの検索戦略を採るか」を同じプロンプトで判断することになる。

## 決定(何をすると決めたか)

**知識検索を独立したサブエージェント(Agent as a Tool)として切り出す。**

```
メイン: understand → validate_plan → act ──[search_knowledge(request)]──▶ 知識検索サブエージェント
                                        ◀──{answer_ja, sources, coverage}── （自分のコンテキストで反復）
                     respond
```

| | |
| --- | --- |
| **呼び出し方** | メインの Tool 1 つ(`search_knowledge`)。**`answer_qa` を置き換える** |
| **入力** | `{request: string}` — 調べてほしいことの自然文。文脈(対象 `spot_id`・日付など)はハーネスが機械的に添付する |
| **出力** | **`{answer_ja, sources[], coverage}`** — 検索結果ではなく、**Agentic RAG エージェントとしての回答**を返す |
| **サブの Tool** | `semantic_search` / `lexical_search` / `get_document` / `web_search`(Tavily)/ `answer`(terminal) |
| **停止条件** | **回数ではなく予算。**§「柔軟性」参照 |

### 柔軟性 — 回数で縛らず、予算で縛る(ユーザー指示、2026-08-01)

**「最大 3 周」のような固定回数の上限は設けない。**

**理由: 質問の難しさは事前に分からない。**「クマは出ますか」は 1 手で終わる。「初心者向けで雨でも楽しめて温泉がある所」は複数の方向を探す必要がある。**回数で縛ると、難しい質問だけが体系的に失敗する。**予算で縛れば、簡単な質問は 1 手で終わり、難しい質問だけが多く回る。

| 種別 | 内容 |
| --- | --- |
| **主予算** | **サブエージェント自身のコンテキスト使用量。**soft 閾値(実効窓の 70%)で「まとめに入れ」を注入し Web の本文取得を抑制、hard 閾値(85%)で Tool メニューを `answer` のみに縮退 |
| **不変条件** | **Tool 実行 0 回の `answer` は無効。**「まず調べること」として差し戻す |
| **安全弁**(チューニングノブではない・事故対策) | ① 同一 `(tool, args)` の再発行は実行せず「試行済み」観測を返す ② 再帰上限(到達時は集めた証拠で `answer` に縮退し、ターンは落とさない) |

### 境界(何をしないか)

- **第二の話者にしない。**ユーザーに見える日本語を書くのは `respond` だけである([30_design/agent_planning_phase.md §8](../30_design/agent_planning_phase.md))。サブエージェントが返す `answer_ja` は **`respond` のための素材**であり、そのまま画面に流さない
- **メインの状態を書き換えない。**プロファイル・旅程・制約・スレッド状態は読み取りのみ
- **メインのコンテキストを共有しない。**共有したら切り出す意味がない。渡すのは `request` と必要最小限の文脈だけ
- **`spot_id` の供給源にしない。**Web 検索の結果は**クローズドワールドの外**にある。サブエージェントの回答から施設名を拾って旅程に入れてはいけない([ADR-0006](0006-recommendation-hybrid.md) の実在性保証を破るため)

## 理由(なぜ他案でなくこれか)

### 1. ADR-0009 が自ら定めた「覆す条件」に、3 つとも該当する

ADR-0009 は決定と同時に、再検討すべき条件を先に書いてあった。**照合すると全部に当たる。**

| ADR-0009 が挙げた条件 | 本件 |
| --- | --- |
| 1 ターンで独立した調査方向を多数探索する必要が生じた | **該当。**Agentic RAG の反復そのもの |
| **16K のコンテキストに情報が収まらず、別コンテキストでの圧縮が必要** | **該当。**上記「文脈 2」。**これが最も強い** |
| Tool 数と専門領域が大幅に増え、単一プロンプトでは Tool 選択の精度が保てなくなった | **該当。**検索だけで Tool が 4 つ増える |

### 2. ADR-0009 が引用した根拠そのものが、この切り出しを支持している

ADR-0009 は Anthropic の報告を「マルチエージェントが効かない理由」として引用した。**同じ文の前半が、本件を名指ししている。**

> "We've found that **multi-agent systems excel at valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools.**"

知識検索サブエージェントは後ろ 2 つ —— **単一コンテキストを超える情報量**と**複数の複雑な Tool** —— に正面から当たる。ADR-0009 が「本件は Tool 5 個、1 ターン最大 3 手、POI 43 件でどれも満たさない」と書いたのは**メインエージェントについての評価**であり、知識検索には当てはまらなかった。

### 3. ADR-0009 の反対根拠は、知識検索には適用されない

**(a) 逐次計画の −70.0%** —— *"Towards a Science of Scaling Agent Systems"* (arXiv:2512.08296) の数字は**「逐次計画」タスクのもの**で、同論文は**分解可能な推論では +80.8%** と報告している。ADR-0009 が退けたのは「理解 → 計画 → 説明」という**依存関係の連鎖を分割すること**であり、それは今も正しい。**知識検索は連鎖の一部ではなく、独立した閉じた仕事である** —— 共有状態(プロファイル・旅程・候補)を必要とせず、質問を受け取って回答を返すだけで完結する。同論文の言う "alignment between coordination and task structure" に照らせば、**ここは分解が構造に合っている側**である。

**(b) MAST の失敗率 41〜86.7%** —— MAST (arXiv:2503.13657) が分析したのは**相互通信するマルチエージェント系**で、失敗モードは役割違反・情報の無視・重複作業・履歴喪失である。**Agent as a Tool は同期的な 1 方向の関数呼び出し**であり、エージェント間の相互通信も、役割交渉も、共有履歴もない。これらの失敗モードの多くが構造的に起きない。

**(c) NFR-3(レイテンシ)** —— **ここは正直に代償である。**下記「影響」に記録する。

### 4. 採らなかった代替案

| 案 | 不採用の理由 |
| --- | --- |
| `answer_qa` を 1 Tool のまま、中で 3 つの検索を**決定的に**呼ぶ | LLM が検索戦略を選べない。「引き直す」判断ができないので、1 回で当たらない構造(文脈 1)に対処できない |
| 検索 4 Tool をメインの plan に並べる(Tool 5 → 8) | 中間状態がメインのコンテキストに乗る(文脈 2)。`get_document` は結果を見ないと選べないのに、plan は結果を見る前に組む |
| **回数上限つきの有界ループ**(最大 3 周) | **ユーザー指示で不採用。**難しい質問だけが体系的に失敗する。予算で縛れば同じ安全性がより良い形で得られる |
| Web 検索を持たせない | `tavily_APIkey` が用意された(2026-08-01)。知識 MD にない最新情報(営業状況・イベント)に答えられる |

## 影響(この決定で生じる制約・やること)

- **[ADR-0009](0009-no-subagents.md) の適用範囲を限定する。**「メインの 1 ターンの逐次連鎖(understand → act → respond)を分割しない」は維持し、**「独立した調査ドメインは切り出してよい」を例外として明記する**
- **[ADR-0008](0008-plan-then-execute.md) はメインについては維持。**`understand` が plan を出し、コードが順に実行する形は変わらない
- **P7「追加 LLM 呼び出しは plan 全体で 1 回まで」を改訂する。**サブエージェント Tool は自身の予算で回るため、この予算の外に置く([30_design/agent_planning_phase.md §1.3](../30_design/agent_planning_phase.md))
- **QA ターンのレイテンシは 2〜3 回固定ではなくなる。**これが本決定の代償である。手当てとして、**検索中の実況を SSE の `state` イベントで出す**([40_api/chat_sse.md](../40_api/chat_sse.md))。QA でないターンは従来どおり 2〜3 回
- **Tool 数は 5 のまま。**`answer_qa` を `search_knowledge` に置き換えるだけで増えない
- `domains/narration/` の下にサブエージェントを実装する。**`domains/conversation/` の下にはエージェントの入れ子を作らない**(ADR-0009 の制約を維持)
- **Tavily は周辺機能として扱う。**サーキットブレーカーを持ち、開放時は「Web 検索は現在利用不可」の観測を返して**知識ベースだけで続行**する(NFR-5)
- **観光フェーズでは使わない。**オフライン動作(FR-4.2)に外部 API は入れられない
