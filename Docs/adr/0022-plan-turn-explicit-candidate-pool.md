# ADR-0022: 旅程新規作成でも挿入プールを明示候補に絞り、カタログ全件への暗黙フル ILS をやめる

- 状態: **提案(2026-08-04)**
- 日付: 2026-08-04
- 関係: [ADR-0021](0021-edit-turn-default-lock.md)(編集ターンの既定固定。**本 ADR はその「初回構築には当たらない」という除外を覆す**)/ [ADR-0005](0005-itinerary-solver.md)(自作 ILS)/ [recommendation_planning.md §4.5](../30_design/recommendation_planning.md) / [agent_react_architecture.md §3.3・§5](../30_design/agent_react_architecture.md)

## 文脈(何が問題か)

ユーザーが実機で「〇〇に行きたいです」と**1 個のスポットのみ**を指名して旅程作成を依頼したところ、返ってきたプランには**複数のスポットが組み込まれていた**(2026-08-04 実機報告)。ユーザーは当初「他ユーザーの『行きたいスポット』が混入しているのでは」とデータ分離バグを疑ったが、コード確認(`repository.py` / `repo.py` の `user_id` フィルタ、`profiles` テーブルの `user_id` 主キー)により**その疑いは否定された**。個人データはすべて `user_id` で正しくスコープされており、そもそも「行きたいスポット」を全ユーザー共有で保存するテーブル自体が存在しない。

実際の原因は `ItineraryService.plan_itinerary`(`backend/app/domains/itinerary/service.py`)が `SolverInput.insertion_pool` を指定していないことである。`insertion_pool=None` は「制限なし」を意味し(`solver.py` `_greedy_fill`)、ソルバーは**鳥海山エリア共通の観光地マスタ(`static.spots` 全 43 件。個人データではなく全ユーザー共通のカタログ)**から効用 ÷ 移動時間が最大のスポットを、時間予算が尽きるまで自動的に詰め込む。これは ADR-0021 が明記した「`plan_itinerary`(新規作成)は従来どおりフル ILS(編集の安定性の問題であり初回構築には当たらない)」という当時の判断どおりの挙動であり、**バグではなく仕様**である。

しかし今回の実機確認で、この仕様は**ユーザーの意図と乖離する**ことが分かった。「1 スポットだけ行きたい」という要求に対し、システムが未指名のスポットを 43 件のカタログから自動選定して追加するのは、ユーザーから見れば「頼んでいないスポットが勝手に入る」という点で ADR-0021 が編集ターンについて是正した問題(「三崎公園は外して」で牛渡川も外れる)と**構造的に同型**である。

ユーザーの方針(2026-08-04、協議): **あくまでユーザーが行きたいスポットで旅程を組む。**「おすすめのスポットで旅程を組んで」のように広く任せる場合は、メインエージェントが `recommend` Tool を使って候補を得たうえで `plan_itinerary` に渡すべきであり、**ツール(ソルバー)側は柔軟性を持たせておいて、メインエージェントの判断でシステムを駆動する**構成が望ましい。

## 検討した対処

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A. 明示候補プール制【採用】** | `plan_itinerary` に任意引数 `candidate_spots`(スポット名の配列。既定空)を追加する。挿入プールは既定で `must_visit ∪ candidate_spots` の解決済み `spot_id` に**限定**する(カタログ全件を暗黙に使わない)。メインエージェントが「おすすめで埋めて」的な要求を受けたときは、先に `recommend` を呼んで候補を得てから `candidate_spots` に渡す | ADR-0021 と対称的で一貫性がある。ツール側は柔軟(候補を渡せばフル ILS 同等に埋まる)を保ちつつ、既定は「頼んだものだけ」になる。`recommend` Tool は既に存在し追加実装が小さい |
| B. `plan_itinerary` にも `allow_refill`(bool)を追加し、true ならカタログ全件から自動充填 | ADR-0021 の `edit_itinerary` とほぼ同じ形。実装は最小 | **却下**。「埋めてよいか/悪いか」の二値では、埋める場合に**何を基準に選ぶか**(プロフィール?タグ?)がソルバー任せになり、結局「頼んでいない場所」が入りうる。ユーザーの方針(メインエージェントの判断で駆動)に合わない |
| C. 現状維持(フル ILS のまま)。UX 文言(respond)で「他のスポットも含めました」と明示するだけ | 実装コストゼロ | **却下**。無言では消えないが、そもそもユーザーが望んでいない挿入が起きる構造は直らない。TREK が指摘する「言語化されない要望の無視」の逆側(頼んでいないことをする)であり、信頼を損なう |

**2026-08-04、ユーザーと協議のうえ A を採用した。**

## 決定(何をすると決めたか)

### 1. `plan_itinerary` に `candidate_spots`(既定空)を追加する

- メインエージェント向け Tool 引数に `candidate_spots: string[]`(スポット名。既定 `[]`)を追加する。**`must_visit` と同じ名寄せ経路**(`name_resolution.py`)で `spot_id` に解決し、解決できない要素は要素単位で落として報告する(C4 と同じ扱い)
- `ItineraryService.plan_itinerary` は `SolverInput.insertion_pool` に **`frozenset(resolved_must_visit) | frozenset(resolved_candidate_spots)`** を渡す(`None` を渡さない)。ソルバーはこの集合の外からは一切スポットを選ばない
- `candidate_spots` は `must_visit` と違い **`require` 制約を生成しない**(強制ではない)。ソルバーは時間予算・効用に応じてこの集合の中から**入れても入れなくてもよい**候補として扱う(既存の貪欲挿入・ILS のロジックはそのまま、対象範囲だけを絞る)

### 2. 候補ゼロは `precondition_unmet` で止める(コードが強制する)

- `must_visit` と `candidate_spots` を解決した結果が**両方とも空集合**になる場合(例: ユーザーが何も指名せず、メインエージェントが `recommend` も呼ばずに `plan_itinerary` だけを呼んだ場合)、旅程計画 SA は `ToolError(precondition_unmet, "旅程に含める観光地が指定されていません。recommend で候補を挙げるか、行きたい場所を確認してください")` を返す
- これにより「空の旅程(スポット 0 件で移動だけの日程)が黙って返る」失敗モードを、起点未解決(既存の `precondition_unmet` パターン、[25 §1-4](../25_known_issues.md))と同じ形でメインエージェントに差し戻す。メインエージェントはこれを見て `recommend` を呼ぶか `ask_user` で聞くかを選べる(プロンプトに判断基準を追記する)

### 3. `recommend` → `plan_itinerary` の連携はメインエージェントの判断に委ねる(新しい専用経路は作らない)

- 「おすすめのスポットで旅程を組んで」のような要求では、メインエージェントが**まず `recommend` を呼び**、結果(`RecommendationResult.spot_ids` などダイジェストに含まれる名前)を**自分の判断で** `candidate_spots` に転記して `plan_itinerary` を呼ぶ。この 2 手構成はメインループの通常の反復(§3.2)でそのまま表現でき、Tool 契約やサブエージェント間の新しい直結経路は追加しない
- メインエージェントのシステムプロンプトに、判断基準の例を追記する: 「ユーザーが具体的なスポット名を挙げていない、かつ `plan_itinerary` を呼ぶ前提として候補が要る場合は、先に `recommend` を呼んで候補を得ること」

### 4. `edit_itinerary` の `allow_refill: true` は対象外(現状維持)

- ADR-0021 が定めた編集ターンの再充填(`allow_refill: true` のときのカタログ全件フル ILS)は、**ユーザーが明示的に補充を求めたとき限定**であり今回の報告とは別の状況(すでに存在する旅程への追加を頼まれている)。本 ADR では変更しない
- ただし同種の懸念(「補充してと言ったら関係ないスポットが入った」)が今後実機で確認されたら、`edit_itinerary` にも `candidate_spots` 的な絞り込みを拡張することを検討する(未着手。[90_backlog.md](../90_backlog.md) に記録)

## 帰結

- 「〇〇に行きたい」だけの依頼は、`candidate_spots` を渡さない限り**〇〇だけの旅程**になる(空き時間は空いたまま)。埋めたければユーザーが望むか、メインエージェントが `recommend` を挟んで明示的に候補を渡す
- **ツール(ソルバー)側の柔軟性は保たれる**: `candidate_spots` に多く渡せば実質フル ILS と同じ挙動になり、渡さなければ厳格に「指名分だけ」になる。制御はメインエージェント(LLM の判断)に委ねられる
- 「候補ゼロで呼ばれる」失敗をコードが検知して差し戻すため、**プロンプトの言い回しだけに頼らない**保証になる(既存の起点未解決と同型のガードレール)
- `plan_itinerary` の Tool 引数が 1 つ増える(`candidate_spots`)。guided decoding スキーマ・`MainPlanItineraryArgs`・`PlanItineraryArgs`・`SolverInput` の受け渡し経路を変更する

## 採らなかった案

- **B(`allow_refill` 方式)**: 上表のとおり。「基準なしに埋める/埋めない」の二値では選定基準が曖昧なまま残る
- **C(現状維持 + 文言のみ)**: 上表のとおり。挙動自体は変わらないため今回の報告に応えられない

## 追記 — 実装レビューによる補強決定(2026-08-04 夜)

初回実装(Sonnet)の完了後、実装レビュー(Codex リミット中につき Opus 5 が代行)で、**決定 2「空の旅程を黙って返さない」を貫通する経路が 2 つ**見つかった。以下を追加で決定する:

1. **解 C(ゆったり版)は `required_spot_ids` を除去対象にしない**(`solver.py` `_relaxed_solution` の是正)。従来の除去対象は `locked` / `protected` / `removal_protected` のみで must_visit を守っておらず、挿入プールが must_visit だけのとき解 C が空旅程になっていた。`notes` があると解選択 LLM が走り(選択器は `spot_ids` / `visit_count` / `concessions` しか見ない)、空の v1 が確定保存されうる — 保存後は `plan_itinerary` が「既に旅程があります」で塞がれ復旧困難。require(§4.4: 未訪問なら大ペナルティ)を意図的に破る解を候補に出すこと自体が設計と不整合であり、是正はソルバー側で行う(本 ADR 当初の「solver.py 内部は変更しない」をこの 1 点に限り解除する)
2. **任意候補がゼロ(`insertion_pool ⊆ required_spot_ids`)のときは単一解とし、解 A/B/C の生成と選択 LLM を省略する**([ADR-0021](0021-edit-turn-default-lock.md) が編集の集合固定で採った形と対称)。プールに自由度がなければ解は実質 1 つで、選択は無意味なうえ空解・重複解を選ぶ事故の温床になる。LLM 呼び出しも 1 回減る
3. **旅程計画 SA の空判定は「実効プール」で行う**: 解決済み `must_visit ∪ candidate_spots` から**日の起終点(endpoint)を引いた集合**が空なら `precondition_unmet`(メッセージは「指定された場所が起点・終点と同じ」の旨を含める)。ソルバーは起終点を挿入対象から常に除外するため、名寄せが起終点にしか解決しないケース(例: メインが同じ地点を `origin_name` と `must_visit` の両方に書く)が名寄せ非空の判定をすり抜けて空旅程になっていた
4. **名寄せ全滅時の `precondition_unmet` メッセージに、落ちた要素・曖昧だった要素を含める**。「観光地が指定されていません」だけでは、メインエージェントが「書いたのに指定されていないと言われた」状態になり、同じ名前での再試行や不要な `recommend` を誘発する
5. **文言の補正(挙動は変えない)**: 「プールの外から一切選ばない」は厳密には **require 制約(§4.4 経路 1)による明示挿入を除く**。`_insert_requirements` は `insertion_pool` の制限対象外(ADR-0021 実装時からの明記済み仕様)であり、「ユーザーが明示した場所は必ず入る」という意図と整合するため挙動は維持し、プロンプト・設計文書の言い回しを補正する。pending の require が有効なターンで must_visit 空の `plan_itinerary` がガードに弾かれる false positive(1 手の浪費。メインは有効制約をコンテキストで見て回復できる)は許容し、[90_backlog.md](../90_backlog.md) に記録する
