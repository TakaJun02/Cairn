# ADR-0016: LoRaWAN の配送は端末駆動の request/response とし、1 通でパック全スポットを返す

- 状態: **決定 (2026-08-01、Phase 3 設計)**
- 日付: 2026-08-01
- 関係: [ADR-0015](0015-pack-asset-composition.md)(天気と混雑は独立した軸)
- 設計: [30_design/realtime_lora.md](../30_design/realtime_lora.md)

## 文脈(何が問題か)

観光フェーズの端末に届く通信は **LoRaWAN のダウンリンクだけ**(FR-4.4、NFR-9)。ここに 2 つの物理的な制約がある。

| 制約 | 中身 |
| --- | --- |
| **LoRaWAN Class A** | **ダウンリンクは、端末がアップリンクを送った直後の受信ウィンドウでしか届かない。**サーバーが任意のタイミングで push することはできない |
| **TTN フェアユース** | 上り電波占有 **30 秒 / 日**、**下り 10 通 / 日**。AS923(日本)DR0〜DR2 のペイロード上限は **51 バイト** |

現行実装は「端末が `spot_id` を文字列で uplink → サーバーが `{"s":"spot_012","w":1,"c":2}`(27 バイト)を downlink」という **1 スポット 1 往復**の形になっている。**この形だと下り 10 通で 10 スポット**しか賄えず、1 日 5〜8 か所を回りながら「昼に天気が変わったのでもう一度聞く」ができない。

さらに、リアルタイム値が無いときに**乱数で捏造して DB に保存していた**([22 §6-2](../22_current_issues.md))ため、「値が無い」という状態を表現する手段がなかった。

## 決定(何をすると決めたか)

1. **端末駆動の request/response にする。**サーバーからの push は設計しない(Class A では作れない)
2. **1 通のダウンリンクで、そのパックに含まれる全スポットのコードを返す**
3. **索引もスポット ID も送らない。**`manifest.spots` の順に **1 スポット 1 バイト**(上位 4 bit = 天気、下位 4 bit = 混雑)を並べる
4. **`0xF` を「不明」に割り当てる**(`spot_realtime` の `NULL` に対応)
5. **`pack_epoch`(1 バイト)を往復に載せ**、端末が持つパックとコード列の並びが一致することを保証する
6. **フェアユースの上限はサーバーが DB で数え**、超過時は publish せずログに出す

```
uplink   [ver, pack_epoch, cur_idx]                    = 3 バイト
downlink [ver, pack_epoch, code_0 … code_{N-1}]        = 2 + N バイト（20 スポットで 22 バイト）
```

## 理由(なぜ他案でなくこれか)

### 1. 律速は帯域ではなく「下り 10 通 / 日」である

51 バイトの上限に対して、20 スポットぶんでも 22 バイトしか使わない。**バイト数には余裕があり、足りないのは通信回数のほう。**したがって「1 通にどれだけ詰めるか」を最大化するのが正しい方向で、符号化を切り詰めることには意味がない。

### 2. 索引を送らないのが最も効く

`spot_id` を文字列で載せると 1 件 8 バイト、1 バイト索引でも 1 件 2 バイトになる。**`manifest.spots` の順に並べると決めれば 1 件 1 バイト**で済む。並びの一致は `pack_epoch` が保証する。

### 3. 差分送信より全量送信のほうが堅い

「変わったスポットだけ送る」は一見効率的だが、**1 通取りこぼすと端末の状態が恒久的にずれる**。全量なら 1 通届けば必ず正しくなる。22 バイトにその価値がある。

### 4. 「不明」を表現できることが要求そのものである

FR-4.5 は値がダミーでよいと言っているが、**無い値を捏造してよいとは言っていない**。`0xF` を持つことで、シミュレータが値を入れていないスポットを `unknown` のまま端末まで運べる。旧実装の乱数捏造([22 §6-2](../22_current_issues.md))はここで構造的に不可能になる。

### 5. 採らなかった案

| 案 | 不採用の理由 |
| --- | --- |
| サーバーからの push | **Class A では不可能。**Class C は端末の消費電力が現実的でない |
| 1 スポット 1 ダウンリンク(現行) | 下り 10 通 / 日を 10 スポットで使い切る |
| JSON をそのまま載せる(現行) | 1 スポットで 27 バイト。全スポットを 1 通に入れられない |
| 差分だけ送る | 取りこぼすと恒久的にずれる。全量でも 22 バイト |
| ACK と再送 | 次の要求で取り直せる。予算を再送に使うほうが損 |
| 予報(`u` / `h`)も載せる | **供給源がサーバーに存在しない**([22 §12-4](../22_current_issues.md) のデッド UI)。作るなら別の要求として立てる |

## 影響(この決定で生じる制約・やること)

- **manifest に `pack_epoch` を持たせる**([packs_pipeline.md §7.2](../30_design/packs_pipeline.md))。`pack_jobs` に `epoch smallint` を足す
- **`manifest.spots` の並びが通信プロトコルの一部になる。**パックを作り直したら `pack_epoch` が変わる。**並び順を後から変えてはいけない**
- **`app.lora_downlinks`(デバイス × 日のカウンタ)を新設する。**プロセス内カウンタにしない
- **`app.users` に `lora_device_id text UNIQUE` を足す**(端末とユーザーの対応)
- MQTT クライアントは lifespan で 1 つ(aiomqtt)。**daemon スレッド + `on_event` をやめる**([22 §6-8](../22_current_issues.md))
- 端末側は **`loraBridge.js` の受信 decode(1 関数)だけ**を変更する。AT コマンド・Join・Android ブリッジは触らない
- **`spotCodes.js`(spot_id ↔ 全体 1 バイトコード)は不要になる**
