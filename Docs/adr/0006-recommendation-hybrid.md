# ADR-0006: POI 推薦は「コードが候補集合を作り、LLM が選択と理由を書く」ハイブリッドとする

- 状態: 承認 (2026-07-30、ユーザーが [30_design/recommendation_planning.md](../30_design/recommendation_planning.md) §8 の論点 3・5・9 に回答)
- 日付: 2026-07-30

## 文脈(何が問題か)

FR-1 は「対話からプロファイルを獲得し、根拠つきで POI を推薦し、天気・混雑をリアルタイムに反映する」ことを求める。旧実装はペルソナ分類(sklearn)+ FAISS 近傍という構成だったが、これは既定としない(ユーザー指示 2026-07-30: 参考にせず作り直し)。

判断を左右する事実として、POI は 43 件しかなく、利用者は数十名規模の研究プロトタイプである。つまり**インタラクションログは構造的に集まらず、コールドスタートが常態**になる。一方で POI 解説の日本語 MD が約 60 本あり、コンテンツ知識は豊富である。タグ語彙は存在するが粗い(自然 16 / 滝 8 / 景勝地 8 / 公園 5 ...)。

手段の候補は 4 つあった。

- **A. 純 LLM**: 43 件全カードをプロンプトに入れ、LLM が選定・順位付け・理由まで一括生成
- **B. 決定的スコアリングのみ**: コードで `score = Σ(interests×tags) + 文脈ブースト − ペナルティ` を計算し top-k。LLM は文章化のみ
- **C. ハイブリッド**: コードでハードフィルタ + スコアリングにより候補 8〜12 件に絞り根拠素材を注釈 → LLM が最終 3〜5 件の選定・順序・理由を候補内 `spot_id` 限定で生成
- **D. 学習ベース**(協調フィルタ・ペルソナ分類・埋め込み近傍)

本文書の初版ドラフトでは **B を既定**としていた(高速・決定的・計測容易)。調査を経てこれを見直す必要が生じた。

## 決定(何をすると決めたか)

1. **案 C を既定構成とする。**コードがハードフィルタとスコアリングで候補 8〜12 件を作り、各候補に根拠素材(一致タグ・所要時間の自然文・天気適合・混雑状況)を注釈し、LLM が最終 3〜5 件を選んで理由を書く
2. **案 B(リランク OFF)を flag として残す。**比較実験のためではなく、**LLM が壊れた/遅いときの縮退経路**として
3. **案 A・D は採用しない**
4. **実装形は「形-2」とする**: `act` が決定的候補を確定した時点で **`state: candidates(provisional)` を即送出してカードを描画**し、その後 LLM リランク(短い guided JSON)→ `state: candidates(final)` → `respond` がストリーミング。1 ターンの LLM 呼び出しは 3 回
5. **UI カードは `state` イベント由来とし、ストリーム本文のパースで状態を作らない**
6. **クローズドワールドを設計原則として固定する**: LLM の出力スキーマ上 POI は `spot_id` でしか表現させない。表示名・座標・写真・説明は必ず DB から引く。LLM が生成した `spot_id` は DB 照合し、不一致なら破棄して再生成する
7. **地理計算を LLM にさせない**: 距離・所要時間は PostGIS/OSRM で計算し「車で約 15 分」の自然文に変換してから注入する
8. **説明の忠実性は「素材の接地」までで止める。**「理由の骨格をコードが決め、LLM は言語化のみ」という構成的忠実性の作り込みと、含意判定による自動検証は**行わない**
9. **リアルタイム反映は文脈の強さで 3 経路に分ける**: 安全に関わる強い文脈は pre-filtering(候補から除外)、中程度はスコア加減点 + 構造化事実の注入、弱い文脈は post-filtering

## 理由(なぜ他案でなくこれか)

- **本件の設定は「ゼロショット LLM 推薦が協調フィルタに匹敵する」と実証された設定そのもの**である。Sanner et al.(RecSys 2023)は、アイテム選好を持たない純粋な言語ベース選好・near cold-start において、ゼロショット LLM 推薦がアイテムベース協調フィルタに匹敵すると報告している。ここで LLM を使わない(案 B)のは、**証拠のある強みを捨てる**ことになる
- **タグ語彙が粗いため案 B 単独の上限が低い。**「静かな場所」「子どもが飽きない」といった未タグ概念に届かない。一方で POI 解説 MD というコンテンツ知識は豊富であり、**コンテンツ知識こそがゼロショット LLM 推薦の性能源泉**である(He et al. CIKM 2023)
- **産業側の「LLM を外せ」は本件に移植できない。**Tripadvisor は推薦生成から LLM を外して 40 秒 → 6.5 秒・品質 +30% を得たが、それは**代わりに置ける強力なレビュー由来レコメンダを持っていた**からである。本件の代替物は粗いタグ上の手書き式にすぎない。移植すべきはその手前の構造 — 候補集合は DB が作る / 順序は決定的エンジンが持つ / レイテンシは品質指標 — であり、案 C はそれを満たす
- **案 C は学術と産業の双方が支持する形**である。学術側は検索 → LLM リランク、産業側は NAVITIME(候補は自社エンジン、LLM は聞き取りと説明)
- **案 D が成立しない。**アイテム 43・ユーザー数十でデータが構造的に不足する。旧実装のペルソナ分類 + FAISS はこの筋であり採用しない
- **形-2 を選んだのは、案 C の唯一の弱点(呼び出し回数)を体感レイテンシで払わずに済むから。**カードは provisional 送出で即描画されるため、形-1(respond に畳み込む・2 回)との体感差は小さい。かつリランクが独立しているので縮退と計測が素直になる。形-3(構造化ストリーミング)は理論上は最良だが、guided decoding 下の日本語散文の品質劣化と途中失敗時のハンドリングが未知数なので、形-2 で計測してから移行を検討する
- **説明の忠実性を作り込まないのは、研究発表に使わないと決まったため**([30_design/recommendation_planning.md](../30_design/recommendation_planning.md) §0.1)。ただしクローズドワールドと根拠素材の注入は**研究のためではなく嘘の理由が出るのを防ぐ品質要件**なので維持する

## 影響(この決定で生じる制約・やること)

- **1 ターンの LLM 呼び出しが 2 回 → 3 回になる**(リランク ON 時)。[ADR-0004](0004-conversation-pipeline.md) の呼び出し予算をこの前提で運用する
- **`presented_spot_ids` をスレッド状態に持つ。**反復推薦(同じ POI を勧め続ける)は LLM 推薦の既知の failure mode なので、スコアでペナルティを課す
- **候補を LLM に渡す順序はスコア降順で固定**し、位置バイアスの感度は評価時にランダム化して確認する。感度が大きければ 1 パス位置不変手法を検討する
- **`spot_id` の実在性を自動テストで機械的に保証する**(不一致ゼロが合格ライン)
- リアルタイム反映の 3 経路はいずれも設定で ON/OFF を切り替えられるようにする(2026-08-01: NFR-7 削除により、記録して比較する部分は落とした)
- プロファイルは構造化 JSONB + 短い自由記述メモの併用とし、`understand` が毎ターン `profile_delta` を返してコードがマージする。`interests` のキーは**データ実在のタグ語彙に enum で強制**する(自由語の増殖を防ぐ)
- プロファイルはチャット上部に**編集可能なチップ列として常時表示**する
- 暫定 → 確定でカードが並び替わる見せ方(スケルトンにするか、暫定を薄く出すか)は実装時に実機を見て決める
