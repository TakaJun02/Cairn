# ADR-0001: 7つのFastAPIサービスを単一プロセスのモジュラモノリスに統合する

- 状態: 提案
- 日付: 2026-07-29

## 文脈(何が問題か)

現行は api / svc-agent / svc-nav / svc-routing / svc-alongpoi / svc-llm / svc-voice の7つのFastAPIプロセスがHTTP/JSONで相互通信する。しかし全プロセスが同一Dockerfile・同一requirements・同一ソースマウントを共有し、Gatewayはエージェント内部のDBモジュールを直接importしている([22 §1](../22_current_issues.md))。つまり独立デプロイ・独立スケール・障害隔離というマイクロサービスの利点は一つも成立しておらず、ネットワークホップ・スキーマ4重定義・タイムアウト予算管理・部分障害・分散デバッグというコストだけを払っている。開発者は1名、運用は単一ホスト、同時利用者は実験規模(NFR-8)。

## 決定(何をすると決めたか)

Pythonで書かれた7サービスを単一のFastAPIプロセス(`app`)に統合する。境界はプロセスではなく、`domains/` 配下のパッケージ+型付きスキーマ+import方向ルールで引く。別プロセスとして残すのは「別技術・別ライフサイクル・別マシン」のものだけ: PostgreSQL、OSRM×2、vLLM×2。

## 理由(なぜ他案でなくこれか)

- サービス間HTTPが関数呼び出しになり、直列HTTPホップのレイテンシ、タイムアウトの入れ子矛盾(Gateway 180s < LLM 600s)、リトライ設計、スキーマ重複が一挙に消える
- 「マイクロサービスを正しく直す」案(個別イメージ・契約・認証・ヘルスチェック整備)は、得られる利点に対応する要求が存在しないため維持コストが正当化できない
- モジュール境界を保っておけば、研究上の必要(例: 特定コンポーネントの別マシン配置)が生じたときに該当ドメインだけをプロセスに切り出すことは引き続き可能

## 影響(この決定で生じる制約・やること)

- コンテナは13→5(db / osrm-car / osrm-foot / app / frontend)
- ドメイン間の依存方向をレビューで守る規律が必要(プロセス境界という物理的強制がなくなるため)
- CPUバウンド処理(KMeans等)は同一プロセスに同居するため、イベントループをブロックしない実行(スレッドオフロード)を徹底する
- 移行は [20_architecture.md §14](../20_architecture.md) のフェーズ計画に従う
