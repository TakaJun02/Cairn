# ADR-0015: パックのアセットを base + overlay の合成にする

- 状態: **決定 (2026-08-01、Phase 2 設計)**
- 日付: 2026-08-01
- 関係: [ADR-0003](0003-pack-generation-jobs.md)(アセット単位の部分成功を第一級で扱う)
- 設計: [30_design/packs_pipeline.md §1](../30_design/packs_pipeline.md)

## 文脈(何が問題か)

観光フェーズの案内は、リアルタイム情報(天気・混雑度)に応じて変化する必要がある(FR-4.3)。現地の端末に届くのは **LoRaWAN の数十バイト**だけ(NFR-9)なので、**変化しうる内容はすべて事前に生成して端末に置いておく**しかない。

旧実装は `(spot_id, situation)` をキーとする**排他的な 5 種**を持っていた(`default` / `weather_1` / `weather_2` / `congestion_1` / `congestion_2`)。端末はそのうち 1 つを選んで再生する。

| 限界 | 中身 |
| --- | --- |
| **「雨で、しかも混雑」が表現できない** | 排他なのでどちらかが必ず消える。優先順位を決めるしかない |
| **本編が状況ごとに作り直される** | 同じスポットの説明が 5 回生成され、状況によって内容がブレる |
| **暗黙のルールがコードに散る** | 「沿道 POI は `default` のみ」という規約が 3 サービス + フロントの計 **7 箇所**に散在([22 §5-5](../22_current_issues.md))。situation を 1 種増やすと 7 ファイルを同時に直す |

**実測(既存パック `fd379dc9…`、2026-08-01 確認)**: 本編 `spot_005.en.mp3` は **436 KB / 54.5 秒**、状況別 `spot_005_weather_1.en.mp3` は **43 KB / 約 5 秒**。旧実装のプロンプトも状況別は「1〜2 文程度」と指示していた。

## 決定(何をすると決めたか)

**アセットを 2 層に分ける。再生は base → 該当 overlay の順。**

| 層 | variant | 内容 |
| --- | --- | --- |
| **base** | `base` | スポットの案内本体。**状況に依存しない** |
| **overlay** | `weather_cloudy` / `weather_rain` | 天気に応じた短い注記 |
| **overlay** | `congestion_mid` / `congestion_high` | 混雑に応じた短い注記 |

1. **天気と混雑は独立した軸として扱う。**雨かつ混雑なら overlay を 2 本続けて鳴らせる
2. **生成対象は `role` で決まる。**`visit`(旅程の訪問地点)= base + overlay 4 種、`pass_by`(沿道 POI)= base のみ。`pack_assets` に `role` 列を持つ
3. **variant の選び方は manifest の `playback_rules` に**データとして書く。フロントのコードに書かない
4. **`pass_by` の base は 20〜40 秒**(`visit` は 45〜60 秒)
5. **雨天代替行程の事前計算は行わない。**代わりに雨 overlay が「近くの雨に強い場所」を 1 件だけ挙げる

## 理由(なぜ他案でなくこれか)

### 1. 設計をデータの実態に合わせる

実測が示すとおり、旧実装の成果物は**すでに「本編 + 短い注記」**だった。排他 5 種という設計だけが、その実態と食い違っていた。合成にすれば表現力が上がり、生成コストは変わらない。

### 2. 直積(3 × 3 = 9)は割に合わない

状況ごとに完結した原稿を作れる代わりに 1 スポット 9 本になる。訪問 10 地点で 90 本。生成時間もディスクも 2 倍近くになり、**その差は「雨で混雑」という 1 通りのため**だけに払われる。

### 3. 本編の品質が状況でブレない

排他方式では雨の日の説明と晴れの日の説明が別々に生成される。同じスポットの由来や見どころが、状況によって違う書かれ方をする理由はない。**base を 1 本にすれば、本編は 1 回だけ良く書けばよい。**

### 4. 暗黙ルールを型とデータにする

「沿道 POI は状況別を作らない」を `role` 列にすると、生成対象が**データから機械的に決まる。**variant を 1 つ足すときに直すのは enum 1 か所と生成規則 1 か所である。`playback_rules` を manifest に載せるのも同じ理由で、**再生の選択規則を端末のコードから追い出す。**

### 5. `pass_by` を短くするのは物理的な要請

時速 40 km で走行中、沿道バッファ 300 m([geo.md §5.2](../30_design/geo.md))の通過に要する時間は約 27 秒しかない。**60 秒の原稿は最後まで鳴らない。**長さは設計値であって好みではない。

### 6. 採らなかった案

| 案 | 不採用の理由 |
| --- | --- |
| 排他 5 種のまま | 「雨で混雑」が表現できない。本編が状況ごとにブレる |
| 天気 × 混雑の直積(9 種) | アセットが 2 倍近くになり、その差は 1 通りのためだけ |
| 端末側で TTS する(状況文をその場で合成) | オフライン端末に音声合成を持たせられない。FR-4.2 の前提が崩れる |
| 状況文を音声にせずテキスト表示だけにする | 案内の主媒体は音声(00_project.md)。運転中・歩行中に読ませない |
| **雨天代替行程を事前計算して同梱** | FR-4.3 は**案内内容**の変化であって行程の差し替えではない。代替行程には別の POI が入るため生成量が倍増し、端末側 UI(Phase 4)に強く依存する |

## 影響(この決定で生じる制約・やること)

- **`pack_assets.variant` の語彙**を `base` / `weather_cloudy` / `weather_rain` / `congestion_mid` / `congestion_high` にする。**`api/schemas` の enum 1 か所**で定義する
- **`pack_assets` に `role` 列を追加する**(`visit` / `pass_by`)
- **manifest に `playback_rules` を載せる。**Phase 3(`realtime_lora.md`)の LoRa ダウンリンクは、**天気と混雑を独立したコードとして送る**必要がある(単一の「状況コード」にしない)
- Phase 4(`offline_field_mode.md`)の端末は、**base の再生後に該当 overlay を順に鳴らす**再生器を持つ。順序は `playback_rules.order` に従う
- **雨 overlay のプロンプトには代替候補 1 件を渡す。**選定は `weather_fit='rain_ok'` かつ `travel_times(car)` 20 分以内の最近傍(コードが決定的に選ぶ)
- 旧実装の `situation` 語彙(`weather_1` など)とアセットのファイル名規約は廃止する
