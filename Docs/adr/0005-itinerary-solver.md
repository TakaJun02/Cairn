# ADR-0005: 旅程プランニングは「LLM が理解と説明、ソルバーが構成」の分業とし、時間割まで持つ

- 状態: 承認 (2026-07-30、ユーザーが [30_design/recommendation_planning.md](../30_design/recommendation_planning.md) §8 の論点 1・2・4 に回答)
- 日付: 2026-07-30

## 文脈(何が問題か)

FR-2 は「対話で旅程を作成・編集し、経路を提示し、セッションを越えて保持する」ことを求めるが、実現手段は要求段階で確定していない([10_requirements.md](../10_requirements.md))。手段の候補は 3 つあった。

- **A. 純 LLM 生成**: 候補 POI と移動時間をプロンプトに入れ、LLM がスケジュールまで書く
- **B. LLM 生成 + コード検証 + リトライ**: A の出力を検証し、違反をフィードバックして再生成
- **C. LLM は制約抽出と説明、時間割の構成はソルバー**

判断を左右する事実として、生成 LLM は `gemma-4-31B`(ローカル vLLM 1 台、max_model_len 16,384)のみであり、外部 API は使えない。POI は 43 件で全件が 1 コンテキストに収まり、OSRM をセルフホストしているため 43×43 の移動時間行列を事前計算できる。1 ターンの LLM 呼び出し予算は 2〜3 回([ADR-0004](0004-conversation-pipeline.md))。

さらに、**旅程の粒度そのものが未決だった**。「訪問順のみ」で割り切るか、時間割(滞在時間・移動手段・到着/出発時刻)まで持つか。この判断はソルバー採用の是非と連動する — 訪問順だけなら 43 地点の巡回順は LLM でもだいたい合うため、ソルバーの投資対効果は小さい。

## 決定(何をすると決めたか)

1. **旅程の粒度は「時間割付き」とする。**訪問順 + 滞在時間 + 移動手段 + 到着/出発時刻を持つ
2. **案 C を主方式とする。**`understand` が制約・希望を構造化抽出し、**コードのソルバー**が時間割を構成し、`respond` が結果を根拠つきで説明する。ソルバーは **TOPTW(Team Orienteering Problem with Time Windows)**として定式化し、**自作 ILS**(貪欲挿入 → shake → 2-opt/or-opt → 時刻割付、数百行・外部依存ゼロ)で実装する
3. **案 B は「検証のみ」を採り、リトライは採らない。**後段バリデータとして `spot_id` の実在性・重複を検査するが、違反時の LLM 再生成ループは実装しない
4. **案 A(純 LLM プランニング)は実装しない。**比較実験の需要がないため(§0.1)
5. **hard 制約は物理的整合のみ**(時刻の整合・日の開始終了・閉鎖中は不可・重複訪問なし・`spot_id` 実在)。**ユーザーの希望はすべてソフト制約 + ペナルティで表現**し、目的関数は `Σ効用 − Σ(weight × penalty) − β × 編集距離` とする
6. **制約は「固定フィールド」ではなく「述語の閉じた集合 × 引数の開語彙」の DSL で表現する**(`not_consecutive(神社)`、`last(温泉)`、`time_window(target, from, to)` など **17 種類**を初期セットとする。全一覧は [30_design/recommendation_planning.md §4.4](../30_design/recommendation_planning.md) 経路 1 の表、enum は [30_design/agent_planning_phase.md §18.2](../30_design/agent_planning_phase.md) の `PredEnum`)
7. **抽出された要望は 4 経路のいずれかに必ず分類される**という不変条件を置き、自動テストで検査する: (1) DSL 述語 (2) POI スコア補正 (3) 複数解からの選択材料 (4) `unmodeled`(反映できなかったと明示)。**無言で破棄する経路を持たない**
8. **ソルバーは解を 3 通り返し**、述語に写らない自由文の要望があるときは LLM がその中から選ぶ

## 理由(なぜ他案でなくこれか)

- **純 LLM 方式が壊れる場所が、本件の要求と正面から一致している。**壊れるのは時間の算術(到着 = 前 POI の出発 + 移動時間、営業時間内か)であり、時間割付きを選んだ以上そこが本体になる。TravelPlanner の実測値は、ツール収集ありの two-stage で GPT-4-Turbo **0.6%**、必要情報を全部渡す sole-planning でも **4.4%**。本件は後者の設定にあたる。さらに Planner-R1 の測定で**素の Qwen3-32B が 0.6%** — これが `gemma-4-31B` に最も近いモデルクラスである。40% 台に達しているのは RL 学習済みモデルのみで、GPT-5 (high) でも 21.2% なので「強いモデルを待てば解決する」筋でもない
- **ソルバー併用の側は数字が 1 桁違う。**FormalVerify 93.9%、Meta の TTG は最適比 0.979 の旅程を約 5 秒で返す
- **B(リトライ)を主方式にできない。**LLM-Modulo は最大 10 反復で 4.4% → 20.6% 止まり、FormalVerify は 1 タスク平均 245.7 秒。1 ターン 2〜3 呼び出しの予算では 1 回しかリトライできず 20.6% すら再現できない。加えて **JSAI2025 の東北大の研究がまさにこの構成(制約管理エージェント + 複数ラウンド修正)を実装して「制約充足には繋がらなかった」と報告している**
- **43 地点は OR 的に些末。**Vansteenwegen らの ILS は **288 地点で最適解とのギャップ 1.8〜2.1%**。ボトルネックは 31B の推論でありソルバーではない。ソルバー 1 回が数十〜数百 ms なので「3 通り作って選ぶ」も成立する
- **TRIP-PAL が自認する弱点(移動時間を乱数でシミュレートした)を本件は最初から持たない** — OSRM を自前で持っているため
- **ソフト制約 + ペナルティを選んだのは、追加 LLM 呼び出しを避けるため。**FormalVerify 型の unsat core は矛盾を説明するだけで代替案を返さず、説明のための LLM 呼び出しが別に必要になる。全部ソフトにすれば常に解が返り、「どの希望をどれだけ譲ったか」が目的関数の内訳として構造化データで得られるので、`respond` の 1 回でそのまま日本語化できる
- **編集距離を目的関数に入れたのは、LLM に任せると壊れる証拠が 3 本あるため** — Flex-TravelPlanner(新しく来た低優先度の選好を既存の高優先度制約より優先してしまう)、TripTide(Qwen2.5-7B は responsiveness 97〜100% だが semantic drift が大きい = 変えすぎる)、arXiv:2605.03308(自己修正の over-sensitivity と erroneous persistence)。**目的関数 1 項で決定的に解ける問題を LLM の暗黙記憶に任せない**
- **DSL + 4 経路を入れたのは、案 C 最大の弱点への対処。**ソルバーはモデル化した制約しか守らず、TREK は「言語化されない要望を満たすことが普遍的なボトルネックで最先端でも未解決」と述べている。固定フィールドの列挙では表現力が足りず、かつ**落としたことに誰も気づけない**のが真の失敗モードである。4 経路の不変条件は「満たせる」ことは保証しないが「**落としたことは必ずユーザーに見える**」ことを保証する。これは正しさの問題を UX の問題に移す設計であり、見えればユーザーが言い直せる
- **自作 ILS を OR-Tools より優先した理由**は、上記 DSL で「述語ごとに任意のペナルティ関数を足せる」ことが設計の中心になり、目的関数を自分で持てることが要件になったから。43 地点では性能差が問題にならず、依存ゼロで挙動が全部読める方が詰まったときに直せる(NFR-1)

## 影響(この決定で生じる制約・やること)

- **データ拡充が必須になる。**`stay_min` / `open_hours` / `weather_fit` / `visit_difficulty` の 4 列がなければ時刻を割り付けられない([30_design/recommendation_planning.md](../30_design/recommendation_planning.md) §6)。43 件・半日〜1 日の作業
- 起動時 or シード時に **OSRM `/table` で 43×43 の car/foot 行列を作り DB に保存**する。`osrm-routed` の `--max-table-size` 既定値 100 を超えないため追加設定は不要(POI が 100 を超えたら引き上げる)
- **ペナルティレジストリ**を 1 つ持つ: `PENALTIES[pred](itinerary, args) -> (violation, 日本語メッセージ)`。述語を 1 個増やす作業が関数 1 個 + メッセージ 1 行になるよう保つ(NFR-1)
- **`understand` の抽出スキーマに `handling` を必須フィールドとして持たせる**(guided decoding の enum)。未知の述語・実在しない引数は例外にせず `unmodeled` に落とす(fail-safe)
- **`respond` のプロンプトに 2 つの必須事項を課す**: 「今回考慮した条件」の列挙と、`unmodeled` への言及
- **ILS の乱数はシード固定**にする(回帰テストの前提)
- 実装時に決める調整項目: ペナルティの重み初期値と `β`、ILS の反復回数・shake の強さ、述語の実装順序(§8.2)
- **`unmodeled` をログに蓄積し、繰り返し落ちる要望を述語追加のシグナルとして使う**(DSL を実データで育てる)
- ハード制約充足率は定義上 100% になるため、**指標として機能しない**。誤差は抽出段に集約されるので、計測の重心を「言ったことが正しく述語に写ったか」に移す([30_design/recommendation_planning.md](../30_design/recommendation_planning.md) §7)
- 最適性ギャップは 43 地点なら厳密解と比較できるので、**実装時に一度測って ILS のパラメータを決めるためだけ**に使う
